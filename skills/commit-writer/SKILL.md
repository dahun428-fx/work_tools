# Commit Writer

스테이징된 변경분을 읽고, **짧고 일관된 한 줄 커밋 메시지**를 만들어 커밋하는 스킬이다.

> **실행 모델**: diff에서 짧은 한 줄 메시지를 뽑는 가벼운 작업이라 **Haiku 모델(`claude-haiku-4-5`)에서 도는 것을 권장**한다. `safe-push` 파이프라인은 이 단계를 Haiku 서브에이전트로 위임해 실행한다. 직접 호출 시에도 Haiku 서브에이전트(Task/Agent 도구, `model: haiku`)에 맡길 수 있다.

## 메시지 형식 (반드시 이 형식)

```
<영어 동사>: <한글 요약>
```

- **앞머리**: 변경 성격을 나타내는 **영어 동사**. 첫 글자 대문자, 뒤에 `: `(콜론+공백).
- **요약**: **한글**로, 무엇을 했는지 간결하게. **약 30자 내외** (앞머리 제외). 마침표로 끝내지 않는다.
- 전체는 **한 줄**. 본문(body)은 기본적으로 붙이지 않는다 — 짧게 유지하는 게 핵심.

**예시:**
```
Add: 로그인 입력값 검증 추가
Fix: 빈 장바구니 결제 오류 수정
Update: 회원가입 안내문구 변경
Remove: 안 쓰는 유틸 함수 삭제
```

### 앞머리 동사 고르기

변경의 핵심 성격으로 고른다 (헷갈리면 가장 큰 변화 기준):

| 동사 | 언제 |
|------|------|
| `Add` | 새 기능·파일·코드 추가 (생성) |
| `Fix` | 버그·오류 수정 |
| `Update` | 기존 동작·내용 변경, 개선 |
| `Remove` | 코드·파일·기능 삭제 |
| `Refactor` | 동작 변화 없는 구조 개선 |
| `Docs` | 문서·주석·README |
| `Test` | 테스트 추가·수정 |
| `Style` | 포맷팅·이름 등 비기능 변경 |
| `Chore` | 빌드·설정·의존성 등 잡일 |

이 목록에 없으면 의미가 맞는 다른 영어 동사를 써도 된다. 중요한 건 **앞머리는 영어, 요약은 한글, 짧게**.

## 진행 방식

1. **변경분 확인** — `git diff --staged`로 **스테이징된 변경**을 본다.
   - 스테이징된 게 있으면 그것만 대상으로 커밋한다.
   - 스테이징된 게 없으면 `git status`/`git diff`로 작업 내용을 보여주고, 무엇을 스테이징할지 사용자에게 확인한다. **임의로 `git add .` 하지 않는다** (의도치 않은 파일이 섞일 수 있다).

2. **변경 성격 파악** — diff를 읽고 무엇이/왜 바뀌었는지 한 문장으로 정리한 뒤, 위 표에서 앞머리 동사를 고른다.

3. **메시지 작성** — 형식대로 한 줄 생성. 요약은 ~30자, 무엇을 했는지가 한눈에 보이게. 너무 길면 핵심만 남기고 줄인다.

4. **커밋 실행** — 생성한 메시지로 커밋한다. 커밋 후 결과(커밋 해시·메시지)를 보여준다.
   ```
   git commit -m "<메시지>"
   ```
   - 변경이 **여러 무관한 작업을 섞고 있으면**, 한 줄로 뭉뚱그리지 말고 "나눠 커밋할까요?"라고 제안한다 (각각의 짧은 메시지와 함께). 단, 사용자가 그냥 다 커밋하라고 하면 가장 큰 변화 기준으로 한 줄을 만든다.

## 좋은 요약을 쓰는 기준

- **무엇을 했는지**를 적는다. "수정함" 같은 공허한 표현 말고 "빈 장바구니 결제 오류 수정"처럼 대상이 보이게.
- **왜인지 자명하면 생략**한다. 30자 안에서 가장 정보가 큰 단어를 남긴다.
- **파일명 나열 금지**. "a.py, b.py 수정" ❌ → 무엇이 바뀌었는지의 의미를 ⭕.
- 추측하지 말 것. diff에서 안 보이는 의도는 지어내지 말고, 보이는 변화에 충실하게.

## 한 줄 요약

> 스테이징된 변경을 읽고 "영어 동사: 한글 요약(~30자)" 한 줄을 만들어 커밋한다. 짧게, 의미 중심으로, 임의 스테이징은 하지 않는다.
