# Troubleshooting Harness

## 개요

장애성 질문을 **매번 같은 사고 흐름**으로 처리해, 단발성 답변이 아니라
**재현 가능한 지식(문서 + 검증 방법)**으로 바꾸는 운영 프로세스다.
핵심은 "원인을 분석해준다"가 아니라 "항상 동일한 산출물을 강제로 만든다"는 데 있다.

모든 산출물은 **한국어**로 작성한다. 단, 코드·명령어·로그·에러 메시지·경로는 **원문 그대로** 유지한다.
흐름의 마지막에는 **항상 파일로 저장**한다.

## 언제 사용하나 (When to Use)

다음과 같은 증상·장애 징후가 보이면 자동으로 이 하네스를 탄다:

- "리포트 다운로드가 안 돼", "PDF 생성은 되는데 저장이 안 돼"
- "Metro가 reload 안 돼", "8081 포트 충돌"
- "ADB에서 device가 안 잡혀", "iOS 빌드가 signing 에러로 실패해"
- "AWS SSH 접속이 안 돼", "Windows 경로 권한 에러"
- 그 외 "안 돼 / 실패 / 에러 / error / 죽어 / 멈춰 / 깨져 / throwing / failing" 류 표현

## 언제 사용하지 않나 (When NOT to Use)

- 단순 정보성 질문("X가 뭐야?", "어떻게 쓰는 거야?")
- 신규 기능 설계·구현 요청 (→ `spec-driven-development` 등)
- 장애가 아닌 일반 코드 리뷰·리팩터링

이런 경우엔 발동하지 않는다. 애매하면 "트러블슈팅으로 진행할게요"라고 한 줄 알리고 시작한다.

## 의존 스킬

| 스킬 | 구분 | 없을 때 설치 명령 | 출처 |
|---|---|---|---|
| `spec-driven-development` | 선택 (장애가 아닌 신규 기능 요청으로 넘길 때) | `npx skills add addyosmani/agent-skills --skill spec-driven-development -g -a claude-code -y` | https://github.com/addyosmani/agent-skills/tree/main/skills/spec-driven-development |

이 하네스 자체는 의존 스킬 없이 동작한다. 신규 기능 요청으로 넘겨야 하는데 위 스킬이 없으면 설치 명령을 한 번 안내하고, 사용자가 승인할 때만 설치한다.

## 하네스 흐름 (고정 순서 — 건너뛰지 말 것)

### 1. 트러블슈팅 대상 판단
증상·장애 징후인지 1초 안에 판단한다. 맞으면 아래 흐름을 끝까지 탄다.
정보성 질문이면 하네스를 타지 않는다.

### 2. 프로젝트 전반 조사 (evidence-first)
추측하기 전에 증거부터 모은다. 범위가 넓거나 불확실하면 **Explore 에이전트**를 띄워
관련 코드·로그·설정을 병렬로 탐색한다.

> 비용 최적화: 파일 탐색·로그 수집 같은 **기계적 조사는 저사양 모델로 위임**한다.
> Explore 에이전트는 `model: "haiku"`(가벼움) 또는 `model: "sonnet"`(중간)로 띄운다.
> 원인 가설·검증 방법 판단·해결 절차 설계 같은 **추론은 세션 모델(메인)**이 직접 한다.

확인 대상:

- **로그**: 에러 메시지·스택트레이스·최근 실패 로그
- **코드/API**: 증상과 연결된 함수·엔드포인트·호출 경로
- **파일·경로**: 산출물이 생기거나 저장되는 위치, 권한
- **환경변수·설정**: `.env`, 빌드 설정, CI 설정, 버전(노드/RN/SDK 등)

> evidence-first 원칙: 증거 없이 원인을 단정하지 않는다. 본 적 없는 코드를 "아마 이럴 것"이라 쓰지 않는다.

### 3. 정보 부족 시 되묻기 (grill 방식)
재현·원인 판별에 **꼭 필요한 것만 1~3개** 먼저 묻는다. 한 번에 하나씩, 추천 답을 함께 제시한다.
나머지 모르는 값은 멈추지 말고 **ASSUMPTIONS 블록**으로 명시한 뒤 진행한다.

```
ASSUMPTIONS (확인 필요):
1. <가정한 환경/조건>
2. <가정한 재현 경로>
→ 틀리면 알려주세요. 일단 이 전제로 진행합니다.
```

### 4. 산출물 생성 (5 필수 + 3 조건부)
아래 8개 섹션을 만든다. 검증 방법(7번)은 **문제 유형에 따라 택1**.
템플릿: `templates/troubleshooting-doc.md` 참조.

**필수 (항상)**
1. 증상 / 문제 요약
2. 환경 정보
3. 원인 후보 / 실패 지점 가설
4. 즉시 확인 명령어
5. 해결 절차

**조건부 (상황에 맞게)**
6. 재현 조건 — 재현 가능한 경우에만
7. 검증 방법 — **택1**
   - 코드 버그·로직 문제 → **테스트 코드**
   - 환경·빌드·배포·네트워크·권한 문제 → **검증 명령어 / 재현 스크립트 / 체크리스트**
8. 재발 방지 체크리스트 — 재발 가능성이 있을 때

### 5. 파일로 저장
산출물을 항상 파일로 남긴다.

- 경로: 현재 프로젝트 루트의 `docs/troubleshooting/`
- 파일명: `YYYY-MM-DD-<slug>.md` (slug은 증상을 영문 kebab-case로, 예: `report-download-fail`)
- repo가 아니거나 `docs/`가 부적절하면 사용자에게 한 줄로 경로를 확인한다.
- 상단에 풍부한 frontmatter(date, project, component, symptom, root_cause, tags, status, severity)를 채운다.

저장 후 저장 경로를 사용자에게 알린다.

## 절대 규칙

1. **테스트 코드 강제 금지** — 모든 장애가 테스트로 풀리지 않는다. 7번은 유형별 택1.
   ADB 인식·signing error·포트 충돌·SSH 접속·경로 권한 등은 검증 명령어/체크리스트가 맞다.
2. **항상 한국어** — 단, 코드·명령어·로그·에러·경로는 원문 유지.
3. **추측 금지, 증거 우선** — 모르면 ASSUMPTIONS로 명시하고 진행한다.
4. **흐름을 끝까지** — 증상만 답하고 끝내지 않는다. 항상 파일 저장까지 간다.
5. **고정 구조 유지** — 섹션 순서·제목을 바꾸지 않는다. 일관성이 자산의 핵심이다.
