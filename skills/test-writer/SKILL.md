# Test Writer

언어와 테스트 프레임워크를 가리지 않고, **변경된 코드와 그 영향 범위**에 대해 올바른 테스트를 작성·실행하고, 실패 시 명확한 피드백을 주는 스킬이다. 보안 관점의 안정성도 함께 점검한다.

핵심 철학: **프레임워크를 하드코딩하지 않는다.** 프로젝트가 이미 쓰는 도구와 스타일을 먼저 읽어내고 거기에 맞춘다. "좋은 테스트의 원칙"은 언어와 무관하게 공통이고, "어떻게 쓰느냐"만 프로젝트마다 다를 뿐이다.

---

## 전체 흐름

1. 환경 감지 → 2. 대상 범위 결정 → 3. 코드 계약 파악 → 4. 케이스 도출(기능+보안) → 5. 기존 스타일대로 작성 → 6. 실행 및 결과 보고

각 단계를 순서대로 진행한다. 특히 6단계(실행·결과 보고)는 **작성으로 멈추지 말고 반드시 이어서 자동 수행**한다.

## 1. 환경 감지 (언어 독립성의 핵심)

테스트를 쓰기 전에 **이 프로젝트의 테스트가 어떻게 생겼는지** 파악한다. 절대 자기 스타일을 강요하지 말 것.

- **언어/프레임워크/실행 명령**을 매니페스트에서 확인:
  - `package.json`(jest/vitest/mocha), `pyproject.toml`·`setup.cfg`(pytest/unittest), `pom.xml`·`build.gradle`(JUnit), `go.mod`(testing), `Cargo.toml`(cargo test), `Gemfile`(RSpec) 등
- **기존 테스트 파일을 최소 1~2개 읽어** 우리 팀 컨벤션을 학습:
  - 파일 위치/네이밍 규칙 (`*_test.go`, `test_*.py`, `*.spec.ts` …)
  - assert 스타일, 사용 중인 mock/fixture 라이브러리
  - 테스트 함수 네이밍 패턴, AAA 구조 사용 여부
- 실행 명령을 확정한다 (예: `pytest`, `npm test`, `go test`, `cargo test`). 특정 파일/패턴만 돌리는 방법도 함께 확인 (`pytest path::name`, `jest <file>`, `go test ./pkg/...`).

기존 테스트가 전혀 없으면, 그 언어의 표준 프레임워크를 고르되 **사용자에게 한 줄로 알린다** ("기존 테스트가 없어 pytest로 잡았어요. 다른 거 쓰시면 알려주세요").

## 2. 대상 범위 결정 — 변경분 + 영향 범위

**작성 대상:**
- 사용자가 파일/함수를 지정했으면 그것을 기준으로.
- 지정이 없으면 `git diff`(또는 `git diff --staged`)로 **변경/추가된 코드**를 대상으로 삼는다.
- **로직이 있는 변경만** 대상. 포맷팅, 주석, 단순 rename, 설정값 변경 등 테스트가 무의미한 건 제외한다.
- 변경된 코드가 **호출하는/호출되는** 인접 부분 중, 이번 변경으로 동작이 바뀔 수 있는 곳을 영향 범위로 식별한다.

코드를 쓰기 전에 **대상 목록을 먼저 보여준다**: "다음에 테스트를 붙일게요 — `a.py:parse_order`, `b.py:apply_discount`. 빠진 거 있나요?" 헛다리를 막고 사용자가 범위를 조정할 기회를 준다.

## 3. 코드 계약 파악

무엇을 검증할지 정하려면 먼저 대상의 **계약(contract)**을 이해해야 한다:
- 입력은 무엇인가? 출력/반환은? 부작용(상태 변경, I/O)은?
- 의존성은 무엇인가 (DB, 네트워크, 시계, 랜덤)?
- 어떤 에러/예외를 던질 수 있는가?
- 신뢰할 수 없는 입력(사용자 입력, 외부 데이터)을 다루는가? → 보안 케이스의 단서.

공개 인터페이스(public behavior)에 집중한다. private 내부 구현은 직접 테스트하지 말고 공개 동작을 통해 간접 검증한다.

## 4. 케이스 도출 — 기능 + 보안

### 기능 케이스
빠뜨리기 쉬운 곳을 의도적으로 노린다:
- **정상 동작** (happy path)
- **경계값** (0, 빈 값, 1개, 최대치, 음수, null/None, 빈 문자열/컬렉션)
- **에러/예외 경로** (잘못된 입력, 권한 없음, 의존성 실패)
- **분기 커버리지** (if/else, switch 각 갈래)

해피패스만 있는 테스트는 거의 가치가 없다. 버그는 대부분 경계와 에러 경로에 숨어 있다.

### 보안 안정성 점검 (항상 자동 — 사용자가 따로 요청하지 않아도 수행)
보안 점검은 **옵션이 아니라 기본 동작**이다. 사용자가 "보안도 봐줘"라고 명시하지 않아도, 모든 대상에 대해 아래 위협을 **항상 자동으로 검토**한다. 기능 테스트만 짜고 보안을 건너뛰는 것은 이 스킬의 실패다.

매 대상마다 아래 항목을 점검하고, 신뢰 경계를 건드리는 항목이 있으면 그에 대한 테스트를 함께 짠다:

- **입력 검증/인젝션**: 신뢰할 수 없는 입력이 쿼리·명령·경로·HTML로 흘러가는가?
  - SQL/NoSQL 인젝션, 명령어 인젝션, 경로 탐색(`../`), XSS 페이로드를 넣어도 안전한지
- **인증/인가 경계**: 권한 없는 주체가 접근/수정 시 거부되는가? 다른 사용자 리소스에 접근 못 하는가?
- **민감정보 노출**: 에러 메시지·로그·응답에 비밀번호·토큰·내부 경로·스택트레이스가 새지 않는가?
- **자원 한계/DoS**: 비정상적으로 큰 입력, 깊은 중첩, 무한 루프 유발 입력에 방어되는가?
- **역직렬화/파일 처리**: 신뢰 못 할 데이터의 역직렬화, 업로드 파일 타입/크기 검증
- **경계 안전성**: 정수 오버플로, 음수 인덱스, 타입 혼동

보안 케이스는 "공격 입력을 넣었을 때 **안전하게 거부/처리**되는지"를 검증하는 형태로 작성한다.

### 취약점은 발견 즉시 보고
보안 점검은 테스트만 짜고 끝나는 게 아니다. 점검 과정에서 **코드 자체의 취약점**(예: 입력 검증 없이 쿼리 조합, 경로 검증 누락, 토큰을 로그에 출력)이 보이면, 테스트 통과 여부와 별개로 **즉시 명시적으로 보고**한다:

```
⚠️ 보안 취약점: {무엇이}
위치: {파일:라인 / 함수}
유형: {SQL 인젝션 / 경로 탐색 / 민감정보 노출 / ... }
위험도: 높음 / 중간 / 낮음
시나리오: {어떻게 악용될 수 있는가}
개선점: {어떻게 막을지 — 파라미터 바인딩, 화이트리스트 검증 등}
```

그리고 그 취약점을 **재현하는 보안 테스트**(공격 입력 → 현재는 통과돼버림)를 함께 작성해, 수정 전후를 검증할 수 있게 한다.

점검 결과 신뢰 경계를 넘는 지점이 전혀 없는 순수 계산 로직이라면, 보안 케이스를 생략하되 **"보안 점검 수행: 신뢰 경계 없음 → 추가 케이스 불필요"처럼 점검했다는 사실 자체를 한 줄로 보고**한다 (조용히 건너뛰지 않는다).

## 5. 작성 — 기존 스타일대로

1단계에서 학습한 컨벤션 그대로 작성한다:

- **구조는 Arrange–Act–Assert** (준비 → 실행 → 검증)가 한눈에 보이게.
- **이름이 명세서**가 되도록 서술형으로: `test_빈_장바구니_결제시_에러` 처럼 "무엇을 보장하는지" 읽히게.
- **한 테스트는 하나의 개념만.** 깨졌을 때 무엇이 깨졌는지 즉시 알 수 있게.
- **구현이 아니라 동작을 검증.** 내부 메서드 호출 여부가 아니라 입력→출력/부작용의 계약을 검증.
- **FIRST 원칙**: Fast(빠름) / Independent(서로 독립, 순서·공유상태 의존 X) / Repeatable(시간·랜덤·네트워크 격리) / Self-validating(자동 판정) / Timely.
- **테스트 더블은 꼭 필요할 때만.** 외부 의존성(DB·네트워크·시계·랜덤)은 격리하되 과한 모킹은 피한다 — 모킹할수록 진짜 동작 검증이 줄어든다.

## 6. 실행 및 결과 보고 (필수 — 작성으로 끝내지 말 것)

**테스트 파일을 만든 것만으로 끝내지 않는다.** 작성했으면 **반드시 같은 흐름에서 직접 실행하고, 실행 결과를 사용자에게 보여준다.** 이게 이 스킬의 신뢰도를 결정하는 부분이다. "테스트 짜뒀으니 돌려보세요"로 끝내면 안 된다 — 사용자가 따로 시키지 않아도 실행·보고까지 자동으로 진행한다.

### 실행 (자동)
- 테스트를 작성한 즉시, 1단계에서 확인한 실행 명령으로 **직접 돌린다.** 실행 여부를 묻지 말 것.
- 범위: **새로 작성한 테스트** + **2단계에서 식별한 영향 범위의 기존 테스트** (회귀 확인).
- 프로젝트 러너의 선택 실행 기능으로 해당 범위만 빠르게 돌린다 (`pytest path::name`, `jest <file>`, `go test ./pkg/...` 등). 전체 스위트가 무겁다면 생략하되, 끝에 "전체는 CI/직접 확인 권장"이라고 안내.
- 실행 환경이 안 갖춰진 경우(러너 미설치 등)는 추정하지 말고, **무엇이 막혔는지와 사용자가 직접 돌릴 정확한 명령**을 보여준다.

### 결과 보고 (항상 — 절대 생략 금지)
실행했으면 그 결과를 **반드시 화면에 보여준다.** 최소 다음을 포함한다:
- 실제 실행한 **명령어**
- **통과/실패 개수 요약** (예: `7 passed, 1 failed`)
- 실패가 있으면 아래 "실패 피드백" 형식으로 각 실패를 설명
- 관련 있는 raw 출력 일부 (너무 길면 핵심만 발췌)

통과만 했더라도 결과(몇 개 통과)를 보여줘야 한다. 결과를 안 보여주고 넘어가는 것은 이 스킬의 실패다.

### 통과해도 한 번 더 본다
통과 자체가 끝이 아니다. **이 테스트가 실제로 코드를 검증하는가**를 점검한다. 어떤 입력을 넣어도 다 통과하는 테스트, 단언이 사실상 비어 있는 테스트는 아무것도 지키지 않는다. 의심되면 단언을 강화한다.

### 실패하면 — 원인 분석 + 개선점 피드백
실패는 두 가지 중 하나다. **반드시 구분해서** 보고한다:

**(a) 테스트가 틀린 경우** (잘못된 기대값, 잘못된 셋업)
- 무엇을 잘못 가정했는지 설명하고, 테스트를 올바르게 고친다.

**(b) 코드에 버그가 있는 경우** (테스트가 실제 결함을 잡음)
- 이게 더 가치 있다. **테스트를 통과시키려고 단언을 약화시키지 말 것.**
- 다음 형식으로 피드백한다:

```
❌ 실패: {테스트 이름}
원인: {왜 실패했는가 — 기대 vs 실제, 어느 입력/경로에서}
판단: 코드 버그 / 테스트 오류
개선점: {올바른 수정 방향 — 어디를 어떻게 고쳐야 계약을 지키는지}
```

- 보안 케이스가 실패하면(= 공격 입력이 통과돼버림) 이건 잠재적 취약점이므로 **명확히 위험도와 함께** 알린다.

### 마무리 요약
실행·보고를 마친 뒤, 짧은 요약으로 닫는다: 무엇을 테스트했고(기능/보안 몇 케이스), 무엇은 생략했고 왜 그랬는지, **실행 결과(통과/실패 개수, 잡아낸 버그), 그리고 발견한 보안 취약점(있으면 위험도와 함께)**. 코드 버그나 취약점을 발견했다면 사용자가 다음 행동(코드 수정)을 정할 수 있게 명확히 제시한다. 이 요약은 실행 결과를 보여준 *다음에* 오는 것이지, 실행을 대체하지 않는다.

## 핵심 원칙 한 줄 요약

> 프로젝트가 쓰는 도구를 그대로 따르되, 경계·에러 케이스와 **보안 점검을 (요청 없이도) 항상 자동으로** 수행하고, **작성에서 멈추지 말고 직접 실행해 결과(통과/실패)를 반드시 보여주며**, 실패하면 "테스트가 틀렸나 코드가 틀렸나"를 가려 올바른 개선점을 주고, 취약점을 발견하면 위험도와 함께 보고한다.
