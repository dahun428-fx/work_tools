# 기획서 작성

## 이 스킬이 지키려는 것

기획서의 목적은 설명이 아니라 **결정**이다. 잘 쓴 기획서와 못 쓴 기획서의 차이는 문장력이 아니라, 읽는 사람이 그 문서만 보고 개발·디자인·법무 판단을 내릴 수 있느냐다.

못 쓴 기획서는 의도를 적고 끝난다 — "마감 전까지 수정 가능". 잘 쓴 기획서는 경계를 적는다 — "14일째 23:59:59까지 적용하고 15일째 00:00부터 종료한다. 모든 일시는 KST 기준". 앞의 문장은 개발자가 다시 물어봐야 하고, 뒤의 문장은 그대로 구현된다.

아래 원칙은 전부 이 한 가지를 향한다: **문서를 읽고 나서 되물을 것이 남지 않게 한다.**

## 문서 골격

### 필수 블록

문서 종류와 무관하게 아래 여섯 개는 넣는다. 빠진 블록이 있으면 그 자리에서 질문이 발생한다.

**1. 개정이력** — 문서 맨 앞. `버전 | 내용 | 작성자 | 작성일자`.
버전은 0.1부터. 작은 변경이라도 행을 추가한다. 기획서는 회람되는 동안 계속 바뀌는데, 이력이 없으면 상대가 어느 버전을 읽고 반응한 것인지 알 수 없다.

**2. 배경 → 문제 → 해결방향 → 목적**
배경은 현상, 문제는 그 현상이 왜 나쁜지, 해결방향은 한 문장, 목적은 2~3개로 쪼갠다.
목적을 여러 개로 쪼개는 이유는 나중에 "이 기능이 성공했는가"를 항목별로 물을 수 있게 하기 위해서다.

As-Is / 문제점 / To-Be 3열 표가 이 블록의 가장 강한 형태다. 현행과 개선을 나란히 놓으면 읽는 사람이 변화의 폭을 한눈에 잰다.

| As-Is | 문제점 | To-Be |
|---|---|---|
| PDF 제공 / 모바일 미지원 | 모바일 확인 불편, 재방문성 낮음 | 핵심 결과를 웹에서 모바일로 확인 |

**3. 정책 (가드레일)** — 시스템이 **하지 않을 일**을 모은 블록.
기획서 곳곳에 흩어진 금지 규칙을 한 곳에 모으면 그대로 개발 가드레일이 된다. 예: "FE/LLM에서 계산하지 않으며 BE 산출 결과만 사용", "투자 권유·수익 보장 표현 금지".
하지 않을 일을 적지 않으면 구현자가 선의로 기능을 넓히고, 그게 사고가 된다.

**4. 케이스 매트릭스** — 상태·옵션이 둘 이상이면 산문 대신 표.
케이스를 **열**, 속성을 **행**에 둔다. 행은 최소한 이만큼: `노출/적용 조건 · 사용자 니즈 · 목적 · 헤드 문구 · 콘텐츠 · 사용자 액션 · 성격`.

세로로 읽으면 한 케이스의 전모가 보이고, 가로로 읽으면 케이스 간 차이가 보인다. 산문으로 쓰면 둘 다 안 보인다.

**5. 상세 규칙** — 번호 매긴 목록. 경계조건을 시각·타임존·예외까지.
여기가 기획서의 밀도가 결정되는 곳이다. 아래 "경계를 끝까지 쓴다" 참조.

**6. 미확정 항목 (의사결정 대기)** — 8열 표. 아래 "미결에는 답을 붙여 보낸다" 참조.

### 상황에 따라 추가하는 블록

- **요청사항 관리표** — 한 문서가 기능 여러 개를 묶을 때: `요청의 건 | 관련 링크 | 기능명 | 현황 | 배포일정`. 현황은 상태 뱃지(작성중 / 검토요청 / 개발 리뷰 요청 / 확정)로.
- **입력 데이터 정의표** — 데이터를 다루는 기능이면: `데이터 | 활용 목적 | 필수 여부`. 필수 여부는 **필수 / 조건부 필수 / 선택** 3단계. 2단계로 하면 "언제 필요한지"가 사라진다.
- **데이터 맵핑표** — 외부 연동이 있으면: `영문명칭 | 국문명칭 | 기준단위`. 단위를 빼면 반드시 사고가 난다.
- **품질 샘플·채점표** — 생성형 기능이나 문안이 결과물인 기능이면 실제 샘플과 채점 기준을 같이 넣는다. 아래 "샘플로 품질을 보인다" 참조.
- **벤치마크** — 참고한 경쟁·유사 서비스와 채택/미채택 판단.
- **외부 링크** — 피그마, 데이터 시트, 이벤트 태깅 문서. 문서 안에서 바로 갈 수 있게.

## 작성 원칙

### 독자는 둘이고, 기본은 비개발자다

기획서는 기획자만 읽지 않는다. 법무·운영·영업·경영진이 읽고 판단해야 하며, 이들은 파일명이나 테이블명을 모른다. 그런데 개발자도 같은 문서를 읽고 구현해야 한다. 두 독자를 한 문서에 담는 방법은 **본문을 비개발자 기준으로 쓰고, 기술 사실은 접어서 붙이는 것**이다.

**본문 규칙** — 비개발자가 본문만 읽고 <b>결정을 내릴 수 있어야</b> 한다. 아래는 본문에서 뺀다.

- 파일명·클래스명·함수명 (`ApplyForm.jsx`, `getSubmission()`)
- 테이블명·컬럼명 (`application`, `rule_version`)
- API 경로·HTTP 메서드 (`POST /api/v1/...`)
- 기술 스택 이름 (Java, Node, MySQL, React)
- 개발 관용어 (전역 싱글턴, 캐스케이드, 스냅샷, 마이그레이션)

**개발 상세 블록 규칙** — 본문 문단 바로 아래에 접어서 붙인다. 여는 문구는 문서 전체에서 통일한다(예: "개발 상세 보기").

- 블록 안에는 **구현자가 확인할 사실**만 넣는다 — 실제 식별자, 경로, 줄 수, 검증 근거.
- **결정은 블록 안에 두지 않는다.** 블록을 접은 채로도 문서가 완결되어야 한다. 블록에만 있는 결정은 비개발자에게 보이지 않으므로 승인받지 못한 결정이 된다.
- 블록이 없어도 본문이 어색하지 않아야 한다. 본문이 "아래 블록 참조"에 의존하면 잘못 쓴 것이다.

**용어 번역 예시** — 같은 사실을 두 층위로 나눠 쓴다.

| 본문 (비개발자) | 개발 상세 블록 |
|---|---|
| 발송 이력을 남긴다 | `notification_log` 테이블에 채널·템플릿·대상 수·발송자 기록 |
| 적용한 심사 기준 버전을 함께 저장한다 | `review_result.rule_version` 스탬프 |
| 본인 화면의 요약 영역이 켜진다 | `dashboard/constants.js:20` `SUMMARY_SECTION` 스텁을 실데이터로 연결 |
| 기존 신청 화면은 연 1회 신청 전용이라 그대로 쓸 수 없다 | `ApplyForm.jsx`(680줄)가 `props.year`를 정체성으로 사용, `window.ApplyDataSource` 전역 결합 |
| 회차별로 신청 내역과 심사 결과를 따로 보관한다 | `campaign` / `application` / `review_result` 3테이블 |

숫자와 고유명사는 본문에도 남긴다. "약 285줄은 가져오고 약 1,300줄은 새로 만든다"는 비개발자도 규모를 가늠할 수 있는 정보이므로 본문에 두고, 그 줄 수가 어느 파일의 것인지는 블록에 넣는다.

### 작성 과정이 아니라 결론을 쓴다

초안에서 무엇이 틀렸고 어떻게 고쳤는지는 **작성자의 이야기지 독자의 정보가 아니다.** 읽는 사람은 "지금 무엇이 맞는가"를 알아야 판단할 수 있고, "예전 버전에서는 이랬는데"는 그 판단에 아무것도 보태지 않는다. 그런 내용은 **개정이력 한 줄로 충분하다.**

| 본문에 쓰지 않는다 | 대신 이렇게 |
|---|---|
| "v0.5까지는 A로 뒀는데 확인해 보니 B였다" | 본문에는 B만. 변경 사실은 개정이력에 |
| "제가 잘못 이해했던 부분이다" | 삭제. 결론만 남긴다 |
| "질문 자체가 잘못 세워져 있었다" | 미확정 항목에서 그 줄을 지우거나 다시 쓴다 |

예외가 하나 있다. **기존에 확정된 결정을 뒤집는 제안**은 "왜 뒤집는가"가 곧 심사 대상이므로 근거를 본문에 남긴다. 단 이때도 쓰는 것은 **기존 결정이 어떤 근거 위에 세워졌고 새로 확인된 사실이 무엇인지**이지, 누가 무엇을 착각했는지가 아니다.

같은 이유로, 독자가 오해하기 쉬운 지점은 **작성 이력이 아니라 주의 사항으로** 적는다. "예전엔 반대로 알고 있었다"가 아니라 "이름만 보면 반대로 읽히기 쉬우니 주의한다"로 쓴다 — 전자는 지나간 일이고 후자는 앞으로 일어날 일이다.

### 사실과 가설을 표시로 구분한다

기획서의 문장은 세 종류가 섞인다 — **확인된 사실**(법령·표준·코드·데이터), **관찰**(경쟁사가 이렇게 한다), **가설**(이렇게 하면 이런 효과가 있을 것이다). 셋을 같은 어조로 쓰면 읽는 사람이 어디까지 믿어야 할지 알 수 없고, 나중에 근거를 물었을 때 답할 수 없는 문장이 남는다.

가장 흔한 사고는 **가설을 단정형으로 쓰는 것**이다. "제출 즉시 결과를 보여주는 것은 응답 품질에 대한 투자다"는 근거가 있어 보이지만 실은 작성자의 추측이다. 이런 문장은 리뷰를 통과해 버리고, 나중에 그 설계가 실패해도 왜 그렇게 정했는지 아무도 모른다.

**쓰는 방법**

- 확인된 사실에는 **출처를 붙인다** — 조문 번호, 지침 번호, 파일과 줄 번호, 조회한 데이터
- 관찰에는 **주어를 남긴다** — "경쟁사 제안서는 ~로 명시한다"
- 가설에는 **가설이라고 쓰고 검증 방법을 붙인다** — "~할 것으로 보고 설계했다. 첫 회차 운영 후 ~를 비교해 확인한다"

가설을 쓰지 말라는 것이 아니다. 기획은 원래 가설 위에 서고, 검증 방법이 붙은 가설은 **지표의 후보**가 된다. 문제는 가설이 사실인 척할 때뿐이다.

표 안에서는 **출처 열**을 하나 두는 것이 가장 확실하다. 항목마다 "표준 서식 문항 3" / "우리 결정"처럼 적으면, 어디까지가 협의 대상이 아니고 어디부터가 우리가 정한 것인지 한눈에 갈린다.

### 표로 사고한다

비교할 것이 둘 이상이면 문장이 아니라 표다. 표를 만들려면 비교 축을 정해야 하고, 축을 정하는 과정에서 빠진 케이스가 드러난다. **표는 서술 도구가 아니라 사고 도구다.**

빈칸이 생기면 그 자리가 곧 미결 항목이다. 빈칸을 없애려고 대충 채우지 말고, 채울 수 없으면 미확정 항목 표로 옮긴다.

### 경계를 끝까지 쓴다

기간·횟수·상태 전환을 쓸 때는 아래를 전부 채운다. 하나라도 비면 개발자가 임의로 정하게 된다.

- **시작과 끝의 시각** — "14일간"이 아니라 "제공 가능일을 포함한 14일째 23:59:59까지 적용하고, 15일째 00:00부터 종료한다"
- **타임존** — "모든 일시는 KST 기준"
- **카운트 기준** — "2회 발화(사용자 turn만 카운트) 시 노출"
- **재발 조건** — "이후 매 2회 발화마다 노출"
- **구체 예시** — "7월 1일 제출한 경우 7월 31일 0시부터 다시 조건에 해당됨"
- **제외 케이스** — "동일 결과 재전송, 단순 정정, 재분석, UI 변경, 장애 복구는 신규로 인정하지 않으며 기존 종료일을 변경하지 않는다"
- **중복·충돌 처리** — "복수 결과가 같은 날 발생하면 해당 날짜 기준으로 한 번만 산정한다"
- **대상 소멸 처리** — "노출 대상이 삭제되거나 제공 불가로 바뀌면 유효한 다른 대상의 존재 여부에 따라 다시 판단한다"

제외 케이스가 특히 중요하다. 정상 흐름은 누구나 상상하지만 "이건 새 결과로 안 치는 것"은 기획자가 정해주지 않으면 아무도 모른다.

### 미결에는 답을 붙여 보낸다

미확정 항목을 질문만으로 적으면 회신이 늦다. 상대가 판단까지 해야 하기 때문이다. 아래 8열로 적으면 상대는 **승인 또는 반대만** 하면 되므로 회신이 빨라진다.

| 구분 | 핵심 전제조건 | 구체 확인·협의 사항 | 필요 산출물 | 미확정 시 리스크 | 우선순위 | 반드시 결정해야 하는 질문 | 권장 방향 |
|---|---|---|---|---|---|---|---|

- **미확정 시 리스크**는 "무엇이 깨지는가"를 구체적으로. "일정 지연" 같은 말은 리스크가 아니다. "AI 상담 진입 채널이 없어 별도 앱 구축 논의로 확장될 수 있음 / 대전제가 흔들림"처럼 쓴다.
- **우선순위**는 최우선 / 높음 / 중간 3단계. 전부 최우선이면 우선순위가 없는 것이다.
- **권장 방향**은 반드시 채운다. 기획자가 답을 모르겠으면 그 항목은 아직 문서에 올릴 준비가 안 된 것이다.

### 대안은 판단까지 적는다

검토한 대안이 있으면 `장점 | 문제점 | 판단` 3열로 남긴다. 판단 칸에는 결론을 한 단어로: **초기 권장 / 비권장 / 단독 적용 비권장 / 다소 김 / 다소 짧음**.

기각한 대안을 남기는 이유는, 남기지 않으면 리뷰 때마다 같은 대안이 다시 제안되기 때문이다. 문서가 그 논의를 한 번에 끝낸다.

### 화면 문구는 기획자가 확정한다

버튼 라벨, 헤드 카피, 로딩 문구, 완료 태그, 토스트, 빈 상태 문구까지 기획서에서 확정한다. "적절한 안내 문구 노출" 같은 서술은 구현자에게 결정을 떠넘기는 것이고, 그러면 서비스 전체의 말투가 흔들린다.

옵션이 여러 개면 옵션별 문구를 표의 열로 관리한다:

| 옵션 | 생성 목적 | 동작 규칙 | 옵션 문구 | 로딩 문구 | 완료 태그 |
|---|---|---|---|---|---|
| 쉽게 | 어려운 용어를 이해하도록 변환 | 쉬운 표현 우선, 수치·주의 기준은 유지 | 더 쉽게 설명해 주세요 | 더 쉽게 답변을 재생성중입니다.. | 더 쉽게 설명한 답변 |

### 샘플로 품질을 보인다

결과물이 문장·이미지처럼 품질을 말로 규정하기 어려운 것이면, **실제 샘플과 채점표**를 문서에 넣는다.

`입력 원본 | 적용 옵션 | 결과물 | 의도 적합도 | 사실·안전성 | 옵션 이행 점수(3점 기준) | 확장 여부`

"자연스럽게 요약한다" 같은 서술로는 개발도 QA도 못 한다. 샘플 3~5건과 채점 기준이 있으면 그게 곧 QA 체크리스트이자 수용 기준이 된다.

### 가능하면 그림을 준비한다

표로 정리되지 않는 것이 두 가지 있다. **분기**와 **흐름**이다. 조건이 갈라지거나 상태가 이동하는 규칙은 글과 표로 쓰면 읽는 사람이 머릿속에서 다시 그려야 하고, 그 과정에서 오해가 생긴다. 그림이 그 수고를 대신한다.

아래에 해당하면 그림을 그린다. 그리기 전에 `artifact-diagramming` 스킬을 읽으면 양쪽 테마에서 읽히는 SVG를 만드는 요령이 있다.

| 상황 | 그릴 것 |
|---|---|
| 조건에 따라 결과가 갈린다 | **판정 플로우** — 입력 → 기준 → 결과 등급. 각 갈래에 조건을 글자로 붙인다 |
| 상태가 이동한다 | **상태 전이도** — 상태를 노드로, 전이 조건을 화살표 라벨로. 되돌아가는 화살표를 빠뜨리지 않는다 |
| 여러 경로가 한 곳으로 모인다 | **경로 수렴도** — 진입 경로가 여러 개인 기능(링크·앱 내부·대리 등록 등) |
| 기간·순서가 의미를 갖는다 | **타임라인** — 기간 규칙을 글로만 쓰면 경계가 안 보인다 |
| 시스템 사이를 데이터가 오간다 | **데이터 흐름도** — 어디서 계산하고 어디에 저장하는지 |
| 화면이 있는 기능 | **와이어프레임** — 화면마다 최소 한 장. 실제 예시 데이터로 채운다 |

그림에는 규칙이 있다.

- **결정 규칙을 담은 그림에는 실제 값을 쓴다.** "조건 충족"이 아니라 "1주일 이상 지속 또는 월 1회 이상". 그림이 사양이 되게 한다.
- **미확정인 부분은 그림 안에 표시한다.** 캡션에 "이 값은 검수로 확정 — 위는 예시"라고 적으면 그림이 잘못 인용되는 것을 막는다.
- **와이어프레임은 실제 데이터로 채운다.** 로렘 입숨이나 "텍스트"라고 적힌 상자는 화면의 정보 밀도를 숨긴다. 사람 이름·수치·부서명을 예시로 넣으면 그 화면이 실제로 감당해야 할 정보량이 드러난다.
- **표로 충분한 것을 그림으로 만들지 않는다.** 항목 나열, 비교, 조건 없는 목록은 표가 낫다. 그림은 분기와 흐름에만 쓴다.

그림을 그릴 수 없는 상황(도구가 없거나 시간이 없을 때)이면 최소한 **텍스트 흐름도**라도 남긴다 — `입력 → [조건①] → 결과A / 결과B` 수준이라도 없는 것보다 낫다.

### 사용자 관점과 사업 관점을 나눈다

기대효과는 두 갈래로 적는다. 사업 관점(계약 전환율, 상품 경쟁력)과 사용자 관점(이해도, 재방문). 한 덩어리로 쓰면 둘 중 하나가 반드시 빠지고, 나중에 성과 측정 지표를 못 만든다.

## 완성 전 체크리스트

문서를 마치기 전에 아래를 훑는다. 하나라도 "아니오"면 그 자리를 채우고 끝낸다.

- [ ] 개정이력이 있고 이번 변경이 기록됐는가
- [ ] 본문에 파일명·테이블명·API 경로가 남아 있는가 (있으면 개발 상세 블록으로)
- [ ] 개발 상세 블록을 전부 접은 채로 읽어도 결정이 가능한가
- [ ] As-Is / 문제점 / To-Be가 표로 대비되는가
- [ ] 시스템이 **하지 않을 일**이 정책 블록에 모여 있는가
- [ ] 케이스가 둘 이상인데 산문으로 설명하고 있지는 않은가
- [ ] 기간·횟수 규칙에 시각·타임존·예시·제외 케이스가 있는가
- [ ] 미확정 항목에 리스크·우선순위·권장 방향이 채워져 있는가
- [ ] 기각한 대안과 그 판단이 남아 있는가
- [ ] 화면에 나갈 문구가 전부 확정돼 있는가 ("적절한 문구" 금지)
- [ ] 분기·흐름을 글로만 설명한 곳이 있는가 (있으면 그림으로)
- [ ] 화면이 있는 기능인데 와이어프레임이 없는가
- [ ] 데이터 항목에 단위와 필수 여부가 있는가
- [ ] 성과를 어떻게 측정할지 적혀 있는가
- [ ] 단정형으로 쓴 문장 중 근거를 못 대는 것이 있는가 (있으면 가설로 표시하고 검증 방법을 붙인다)
- [ ] 표준·법령에서 온 항목과 우리가 정한 항목이 구분돼 있는가
- [ ] 읽고 나서 되물을 것이 남았는가

## 안티패턴

| 이렇게 쓰지 않는다 | 이렇게 쓴다 |
|---|---|
| "마감 전까지 수정 가능" | "마감일 23:59:59까지 수정 가능하며, 마감 직후 상태를 동결한다(KST)" |
| "적절한 안내 문구 노출" | 실제 문구를 따옴표로 확정 |
| "추후 협의" | 미확정 항목 표에 리스크·우선순위·권장 방향과 함께 |
| "사용자가 원하는 대로" | 옵션을 열거하고 각 옵션의 동작 규칙을 표로 |
| 케이스 3개를 문단 3개로 설명 | 케이스 3개를 표의 열 3개로 |
| 우선순위 전부 "최우선" | 최우선 / 높음 / 중간으로 실제 배분 |
| 기각한 대안을 지움 | 장점·문제점·판단으로 남김 |
| 판정 분기를 문단으로 서술 | 판정 플로우 그림 + 각 갈래에 실제 조건값 |
| 와이어프레임을 "텍스트" 상자로 채움 | 사람 이름·수치·부서명 등 실제 예시 데이터로 |
| 본문을 접어서 숨김 | 회람·인쇄되는 문서는 펼친 상태가 기본 |
| 본문에 파일명·테이블명·API 경로 | 본문은 일상어로, 식별자는 개발 상세 블록으로 |
| "이전 버전에서는 ~였다" 정정 서술 | 본문엔 결론만, 변경 사실은 개정이력에 |
| 개발 상세 블록에만 있는 결정 | 결정은 본문에 — 블록을 접어도 문서가 완결되게 |

## 참고 자료

- `references/templates.md` — 각 블록의 복사해 쓰는 표 템플릿 모음. 새 기획서를 시작할 때 이 파일을 열어 필요한 블록을 가져온다.
- `references/examples.md` — 실무 기획서에서 뽑은 좋은 문장 예시. 경계조건 서술, 리스크 표현, 마이크로카피의 실제 수준을 확인할 때 본다.

## 산출물 형식

사용자가 형식을 지정하지 않았다면 마크다운 문서로 쓴다. 다만 이 스킬의 표들은 열이 많아(특히 미확정 항목 8열) 좁은 화면에서 읽기 어려우므로, 문서를 사람이 회람할 목적이면 아티팩트로 발행하는 편이 낫다 — 그때는 `artifact-design` 스킬을 먼저 읽는다.

기존 문서를 고치는 경우, 원문의 형식(엑셀 시트 구성, 마크다운 구조)을 유지하고 블록만 채운다. 형식을 바꾸면 회람 이력이 끊긴다.
