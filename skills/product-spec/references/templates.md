# 블록 템플릿 모음

새 기획서를 시작할 때 필요한 블록을 여기서 가져다 채운다.
표의 열 이름은 바꾸지 않는 편이 좋다 — 팀이 같은 열 이름을 반복해서 보면 빠진 칸이 눈에 띈다.

## 목차

1. 개정이력
2. 요청사항 관리표
3. 배경·목적
4. As-Is / 문제점 / To-Be
5. 기대효과
6. 정책 (가드레일)
7. 케이스 매트릭스

10. 상세 규칙
11. 입력 데이터 정의

## 2. 요청사항 관리표

한 문서가 기능 여러 개를 묶을 때. 문서 앞부분에 두어 전체 범위를 먼저 보인다.

| 요청의 건 | 관련 링크 | 기능명 | 현황 | 배포일정 |
|---|---|---|---|---|
| 1. 〇〇 | 피그마 / 데이터 시트 | [기능] 〇〇 | ✅ 개발 리뷰 요청 | |
| 공통 | 이벤트 태깅 문서 | - | 작성중 | |

현황 값: `작성중` / `검토요청` / `✅ 개발 리뷰 요청` / `확정` / `보류`

## 3. 배경·목적

```
[배경]
현상을 한두 문장으로. 판단이 아니라 사실.

[문제]
그 현상이 왜 나쁜지. 누구에게 어떤 불편이 생기는지.

[해결방향]
한 문장. 무엇을 어떻게 바꾸는지.

[목적]
① …
② …
③ …
```

목적을 번호로 쪼개는 이유는 나중에 항목별로 달성 여부를 물을 수 있게 하기 위해서다.

## 4. As-Is / 문제점 / To-Be

| As-Is | 문제점 | To-Be |
|---|---|---|
| 현행 방식 | 그래서 생기는 불편 | 바뀌는 모습 |

행은 4~6개가 적당하다. 현행의 서로 다른 측면(제공 형식 / 정보 깊이 / 상호작용 / 상품성 / 후속 연결)을 잡으면 자연스럽게 그 정도가 나온다.

## 5. 기대효과

사업 관점과 사용자 관점을 반드시 나눈다. 한 덩어리로 쓰면 둘 중 하나가 빠진다.

```
[사업 관점]
…

[사용자 관점]
① 〇〇 : …
② △△ : …
```

## 6. 정책 (가드레일)

시스템이 **하지 않을 일**을 모으는 블록. 흩어두면 개발 가드레일이 되지 못한다.

| 구분 | 정책 |
|---|---|
| 계산 주체 | 〇〇에서 계산하지 않으며, △△ 산출 결과만 사용한다 |
| 표현 제한 | 투자 권유, 수익 보장, 특정 상품 추천 표현을 사용하지 않는다 |
| 범위 제한 | 사용자가 묻지 않은 주제로 확장하지 않는다 |
| 사실 보존 | 거래 금액·분류 결과·승인된 근거 문서의 사실을 변경하지 않는다 |

## 10. 상세 규칙

번호 매긴 목록으로 쓴다. 각 항목이 하나의 판정 가능한 규칙이어야 한다.

```
1. [적용 범위] …를 포함하여 총 N일간 적용한다.
2. [경계 시각] N일째 23:59:59까지 적용하고, N+1일째 00:00부터 종료한다. 모든 일시는 KST를 기준으로 한다.
3. [반복 조건] 기간 내 …가 있으면 … 때마다 노출한다. 단, …를 선택하면 이후 노출하지 않는다.
4. [미도달 처리] 기간 내 …가 한 번도 없으면, 기간 종료 후 최초 …시 1회 노출한다.
5. [전환 규칙] … 이후에는 기본 상태로 전환한다.
6. [1회성 보장] …는 최초 1회만 노출한다. 정상 노출 이후에는 다음 진입부터 기본 상태를 적용한다.
7. [종료 후 보존] 종료된 이후에도 기존 데이터와 콘텐츠는 …를 통해 계속 제공한다.
8. [재산정] 기존 상태와 관계없이 새로운 …가 발생하면 그 시점을 기준으로 새로 산정한다.
9. [복수 발생] 복수가 같은 날 발생하면 해당 날짜 기준으로 한 번만 산정한다.
10. [제외 케이스] 동일 건 재전송, 단순 정정, 재분석, UI 변경, 장애 복구는 신규로 인정하지 않으며 기존 종료일을 변경하지 않는다.
11. [대상 소멸] 대상이 삭제되거나 제공 불가 상태로 바뀌면 다른 유효한 대상의 존재 여부에 따라 다시 판단한다. 유효한 대상이 없으면 즉시 종료한다.
```

10~11번(제외 케이스, 대상 소멸)은 빠뜨리기 쉬운데 실제 운영 사고는 대부분 여기서 난다.

## 11. 입력 데이터 정의

| 데이터 | 활용 목적 | 필수 여부 |
|---|---|---|
| | | 필수 |
| | | 조건부 필수 |
| | | 선택 |

필수 여부는 3단계로. 2단계로 하면 "언제 필요한지"가 사라진다.
조건부 필수는 조건을 같이 적는다 — "소비 내역 분석·예산 질문에 개인화 적용".

## 12. 데이터 맵핑

| 영문명칭 | 국문명칭 | 기준단위 |
|---|---|---|
| Amount | 결제금액 | 원 |
| TxAt | 결제일시 | KST, yyyy-MM-dd HH:mm:ss |

단위를 빼면 반드시 사고가 난다. 외부 연동이면 허용 범위·값 형식도 열로 추가한다.

## 13. 미확정 항목 (의사결정 대기)

이 스킬에서 가장 중요한 표. 질문만 던지지 말고 권장 방향까지 채워 보낸다.

| 구분 | 핵심 전제조건 | 구체 확인·협의 사항 | 필요 산출물 | 미확정 시 리스크 | 우선순위 | 반드시 결정해야 하는 질문 | 권장 방향 |
|---|---|---|---|---|---|---|---|
| 1. 〇〇 | | | | | 최우선 | | |
| 2. △△ | | | | | 높음 | | |
| 3. □□ | | | | | 중간 | | |

- 리스크는 "무엇이 깨지는가"로. "일정 지연"은 리스크가 아니다.
- 우선순위가 전부 최우선이면 우선순위가 없는 것이다.
- 권장 방향을 못 채우겠으면 그 항목은 아직 올릴 준비가 안 됐다.

## 14. 품질 샘플·채점표

결과물이 문장·이미지처럼 말로 규정하기 어려운 것이면 샘플 3~5건과 채점 기준을 넣는다.

| 입력 원본 | 적용 옵션 | 결과물 | 의도 적합도 | 사실·안전성 | 옵션 이행 점수(3점) | 확장 여부 |
|---|---|---|---|---|---|---|

이 표가 그대로 QA 체크리스트이자 수용 기준이 된다.
